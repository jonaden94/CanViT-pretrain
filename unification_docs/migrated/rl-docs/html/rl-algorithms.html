How QReg, PG and Flow are implemented

An implementation-level walkthrough of the three learning algorithms in CanViT-PyTorch-RL: what each one consumes, what it outputs, and exactly how it is trained.

Assumed knowledge & scope. You know CanViT and the active-vision method cold — the recurrent canvas, glimpses, viewpoints, the frozen ADE20K segmentation probe. This document does not re-explain any of that. It explains only the layer on top: the policy network and the code that trains it. Everything below refers to real symbols in src/canvit_pytorch_rl/; each block cites its file:line. Because you may not remember every component's exact name, each one is introduced with what it is and what role it plays before any code.
Orientation — where this sits in the CanViT picture. In CanViT, perception is a recurrence: a sequence of glimpses is written into a persistent canvas, and a readout head turns the canvas into predictions. The question CanViT itself doesn't answer is which glimpses to take — in the CanViT experiments that sequence is scripted or heuristic (coarse-to-fine, random, entropy-guided). This repo replaces the scripted glimpse-chooser with a learned one: a small network that, at each step, reads the current canvas and picks the next viewpoint. Nothing inside CanViT changes — the backbone and the segmentation probe stay frozen; the only new trainable object is that controller. So read this whole document as "how the glimpse-chooser is built and trained," with CanViT sitting underneath as a fixed environment. The three algorithms (QReg, PG, Flow) are three ways to train that one controller.

1 · The shared substrate

QReg and PG are two readings of one controller network trained by one loop; before either loss runs, the same machinery builds the controller's input, its action menu, and its reward. That shared machinery is the bulk of the codebase — the algorithms in §2–§3 are then only a handful of lines each. We walk it in the order data flows: the frozen world (1.1) → the actions it can take (1.2) → the controller's input features (1.3) → the controller itself (1.4) → what counts as a good move (1.5) → how experience is collected (1.6) → how the reward is normalized before training (1.7).

1.1 · The frozen oracle — the fixed world

What it is: the frozen CanViT-plus-probe, loaded once and used as a fixed environment the controller acts in. Concretely it is a CanViTForSemanticSegmentation = the CanViT recurrence you know (seg.canvit) with an ADE20K linear segmentation probe bolted on top (seg.head, trained separately over in canvit_specialize). Its role: it does triple duty and is never trained (except the optional unfreeze="probe" rung) — (i) it is the world: applying a glimpse advances CanViT's recurrence to a new state; (ii) it featurizes a state into the controller's input; (iii) it scores the reward. Everything in §1.1–§1.7 is either this object or something wrapped around it.

training/train.py:56–59 
seg, _, _ = setup(cfg)              # CanViTForSemanticSegmentation.from_pretrained_with_probe(...)
seg.requires_grad_(False)             # the whole perception stack is frozen
if cfg.unfreeze == "probe":         # optional rung 1: train ONLY the probe head
    seg.head.requires_grad_(True)
  • seg.canvit — the recurrent CanViT. Used as the environment: seg.canvit(glimpse, state, viewpoint) → RecurrentState, and for init_state / get_spatial. RecurrentState is CanViT's own recurrence carrier (from canvit_pytorch): a dataclass with canvas [B, n_canvas_registers + G², canvas_dim] and recurrent_cls [B, 1, local_dim]. The RL layer treats it as the opaque "state s" and only ever reads .canvas — via get_spatial, which strips the register tokens to the G² spatial tokens; recurrent_cls is never touched.
  • seg.head — the segmentation probe: canvas spatial tokens → [B, 150, G, G] per-pixel logits. This is what the reward and the entropy features read.
  • seg.canvas_dim — the channel width D of a canvas token; feeds the network's canvas_dim.

1.2 · The action space — the controller's menu of glimpses

What it is: the finite set of viewpoints the controller may pick from at each step — its action menu. Why discrete: a CanViT viewpoint is a continuous (center, scale), but the controller scores a fixed enumerable set of them, so "choose the next glimpse" becomes "pick one of A cells" — cheap to score all at once and to argmax at deploy. (The Flow algorithm in §4 is the road-not-taken where the action stays continuous.) The set: for each scale s, a cpa×cpa grid of centres tiling the safe box [−(1−s), 1−s]² so the glimpse box never leaves the image. Placement resolution is decoupled from scale, so same-scale glimpses overlap. Default: 2 scales × 16 × 16 = 512 candidate viewpoints.

1.3 · StateEncoder — turning the canvas into the controller's input

What it is: the translator between CanViT's raw canvas and what the controller reads. Its job: take a RecurrentState and emit a compact, informative feature map [B, C, 32, 32]. Consumes the state — plus, optionally, that state's probe logits (the ADE20K per-pixel class logits, i.e. seg.head applied to the canvas, [B, 150, G, G]). Why optional: computing them is a seg.head forward, and whatever invokes the encoder — in training the rollout loop of §1.6 — has already computed them at this state for the CE reward, so it passes them in and the entropy features reuse that single call rather than doing a redundant second one. If nobody supplies them (logits=None), the encoder computes them itself. It builds six named feature groups; only two touch the probe, the other four are pure statistics of CanViT's canvas. This is also where deliberate feature engineering happens — the callout below says what and why.

training/config.py:14 · policy/features.py:43–58 
FEATURE_GROUPS = ("ent", "ent_delta", "cos_prev", "cos_init", "ln_feat", "feat_delta")
# ent, ent_delta      : PROBE-derived — per-position entropy of seg.head logits, and its change  (1 ch each)
# cos_prev, cos_init  : canvas-only  — 1 − cosine sim to prev state / to the blank template       (1 ch each)
# ln_feat, feat_delta : canvas-only  — LayerNormed canvas features, and their change    (canvas_dim ch each)
What's happening here: feature engineering, and why. Rather than feed the controller CanViT's raw canvas and hope it learns everything, the encoder hand-computes summaries known to matter for "where to look next." Three flavors:
  • Injected priors — ent, cos_init. ent (per-position probe entropy) is literally the signal CanViT's EntropyGuidedC2F baseline uses to pick glimpses; handing it to the controller means it starts from that heuristic instead of having to rediscover it. cos_init (distance from the blank canvas) is an engineered "how much has this region filled in yet" / novelty signal.
  • Temporal-difference features — ent_delta, cos_prev, feat_delta: "what changed since my last glimpse." This matters because the controller network (§1.4) is feedforward and per-state — it has no memory of its own, so it cannot compute change internally. The encoder supplies that memory externally by holding a rolling reference to the previous state and differencing against it (next paragraph).
  • The near-raw representation — ln_feat (canvas_dim-wide), just the LayerNormed canvas features. Barely engineered; it's here so the controller isn't boxed into the hand-crafted scalars and still has CanViT's full learned canvas to reason over.
Why engineer at all: the supervision is extremely sparse — one sampled action per scene (§1.6) — and the controller is small, so engineered features buy sample-efficiency and inject useful priors. The cost is baked-in assumptions; in principle a larger, recurrent controller fed the raw canvas across the trajectory could learn ent/deltas/novelty itself, at more data and compute. Two hedges keep it honest: the Frontend has learned per-group gates (the net reweights each group — it ends up favoring ent/ent_delta), and cfg.feature_groups is an ablation knob (train on any subset to measure each group's contribution).

Mechanically, "the state" here is just CanViT's canvas (its persistent scene memory): get_spatial pulls the G² spatial tokens, reshaped to a [B, D, 64, 64] map. To define the *_delta / cos_prev groups the encoder keeps a rolling reference to the previous state; reset() rolls it back to the blank-canvas template at the start of every rollout, so the very first (t0) deltas read "deviation from blank" instead of dead zeros.

1.4 · ViewpointScorer — the controller itself

What it is: the controller — the one new trainable network, the learned stand-in for CanViT's scripted glimpse-chooser. Its job: look at the current state's features and rate every candidate viewpoint. Consumes feats [B, C, 32, 32] (from §1.3); outputs one scalar per candidate — a score map [B, n_scale, cpa, cpa], i.e. one number per dot in the §1.2 grid. At deploy the next glimpse is simply the argmax. It is objective-agnostic: the same forward pass is read as Q-values (QReg, §2) or as policy logits (PG, §3).

  • Frontend — per-channel BatchNorm to scale-equalise the heterogeneous groups, then each group gets its own 1×1 projection + affine LayerNorm + learned gate, summed and mixed by a token-MLP net.py:66–92.
  • Body — a ConvNeXt-V2 U-Net: the encoder pools 32→16→…→1 (a global bottleneck, so every score sees the whole scene), the decoder rebuilds a 32×32 map registered to the full image net.py:144–154.
  • Readout — per scale, grid_sample the decoder map at that scale's safe-box centres and pass through one shared head (+ a per-scale embedding), so score cell (i,j) is read exactly where glimpse (i,j) would land net.py:156–160.
  • Dueling (QReg only) — Q = V(s) + mean-zero A(s,a), V a small head on the mean-pooled input features. Argmax (hence deploy) is unchanged net.py:161–163.
def forward(self, feats) -> Tensor:            # feats [B, C, 32, 32]
    h = self.frontend(feats)
    ...                                       # U-Net → decoder map d [B, width, 32, 32]
    vals = [ self.head(F.grid_sample(d, self.sb_grids[k]...) + self.scale_emb[k])
             for k in range(n_scale) ]
    q = torch.cat(vals, dim=1)                  # [B, n_scale, cpa, cpa]
    if self.vhead is not None:                  # dueling: recentre + add V(s)
        flat = q.reshape(b, -1)                   # [B, A]  (A = n_scale·cpa²)
        q = (flat - flat.mean(1, keepdim=True) + self.vhead(feats.mean((2,3)))).reshape(q.shape)
    return q

1.5 · The reward — what counts as a good glimpse

What it is: the signal the controller is trained to maximize — the definition of a "good move." Why this form: the downstream task is segmentation, so a glimpse is good if it makes the frozen probe more correct. The reward for a glimpse is the fraction of the probe's remaining per-image cross-entropy that it removes — fractional (not absolute) so easy and hard scenes contribute comparably. The cross-entropy is measured against masks — the ground-truth ADE20K label map for the batch, a per-pixel class index [B, H, W] (values 0–149, or 255 = ignore). It's a fixed dataset label; the controller never sees it, only the reward derived from it. There is no discount, no bootstrap, no target network — it is directly measured, dense, and available at every step.

rt = ( CEt − CEt+1 ) / CEt
scoring.py:33–38 (per_image_ce) · canvas_ops.py:18–29 (ce_from_logits) 
def per_image_ce(logits, masks) -> Tensor:      # mean CE over VALID pixels, per image → [B]
    ce = F.cross_entropy(logits, masks, ignore_index=IGNORE_LABEL, reduction="none")
    valid = (masks != IGNORE_LABEL).sum((1,2)).clamp(min=1)
    return ce.sum((1,2)) / valid

Training scores CE at score_res=128 (masks downsampled, logits upsampled to 128²) — ~2× cheaper, candidate ranking preserved to Spearman ≈ 0.999. Final evaluation is always full 512².

1.6 · The rollout — collecting training experience

What it is: the loop that manufactures training data by letting the controller actually play. Why it's needed: to train the controller (§1.4) we need examples of the form (a state the controller faces, the glimpse it chose there, the reward that glimpse earned). But here's the catch that makes this different from ordinary supervised learning — the states the controller faces depend on its own earlier choices: after it picks glimpse 1, the canvas it must reason over for glimpse 2 is whatever glimpse 1 wrote. So you can't just harvest states from a dataset; you have to generate them by running the controller forward, step by step, on a batch of images. That play-through is the rollout (rollout_samples). It consumes a batch of images, masks and produces one training sample per state it visits.

One rollout is just the §1.1–§1.5 pipeline run in a loop. Starting from the full-scene state and repeating H = train_horizon times:

  1. Start (t0): take the full-scene glimpse → the initial RecurrentState (§1.1, full_scene_state).
  2. Featurize the current state → feats (§1.3, the StateEncoder).
  3. Score & pick: the controller scores all candidates from feats (§1.4); choose one candidate — that's the glimpse to take.
  4. Record the sample for this state: (the feats it saw, the candidate index it picked, and — once we've acted — the reward).
  5. Act & measure: apply that glimpse to advance to the next state (§1.1, advance_state), and compute the reward = fractional CE drop from this glimpse (§1.5).

Two efficiencies worth noticing. One sample per state (K=1): at each state we log only the one candidate we actually took, not all 512 — cheap, and enough (§1.7 explains why one is sufficient). And the glimpse we took does double duty — it is both the labelled action and the move that advances the rollout — so a whole training sample costs only ≈ one extra CanViT recurrence step.

Intuition — why the rollout follows the controller's own choices (the DAgger idea). The natural worry: which candidate should advance the rollout in step 5? Suppose we advanced using random glimpses. Then we'd train the controller on canvases that random looking produces — but at deploy the controller follows its own argmax, reaching quite different canvases. We'd have trained it on states it never actually visits, and it would flail on the ones it does. The fix: advance the rollout (mostly) under the controller's own deployed choice — its eval-mode argmax — so the states it learns on are exactly the states it will face at deploy. That train/deploy match is the whole point of DAgger (collect data under the learner's own policy); the twist here is that the label at each state is a measured reward, not an expert's action. Concretely, how the advancing action is chosen depends on the objective: QReg uses ε-greedy — the controller's argmax with probability prime_on_policy, otherwise a random candidate (so it still explores); PG samples from the softmax over candidate scores (required so the reward is a valid score-function signal — §3).

1.7 · The target standardiser — one RunningNorm per rollout depth

Two different normalizations act on the reward, along two different axes — it's worth keeping them straight, because they do not do the same job:

  • Across scenes — the fractional division (already done, §1.5–§1.6). Absolute CE drops are not comparable between a hard scene (high CE) and an easy one (low CE). Dividing each drop by the state's own CE (/base_ce) converts it to a fraction of current error removed, which is comparable across scenes. This is what handles "different scenes have vastly different reward scales." Note it does not flatten scenes to equal weight — a scene that genuinely had more to gain still yields a larger fraction, and should weigh more. That's signal.
  • Across the training-time stream — the RunningNorm (this section). It is a single global bias-corrected EMA of the fractional signal's mean and std; it standardises (x − mean)/std. It cannot per-scene-normalize (it applies the same two scalars to every sample), and it is not trying to. It does two other things:
  1. Centering (subtract the running mean) → a baseline / advantage. The mean fractional reward is positive — almost any glimpse lowers CE a bit. Regressing or weighting on the raw positive number would push every action up, with no contrast. Subtracting the mean turns the target into "better or worse than the typical move at this depth": for PG that is literally the advantage baseline (sign decides up- vs down-weighting), for QReg it centers the regression target.
  2. Unit scale over training time (divide by the running std) → stationary gradients. As the policy improves, the raw fractional rewards shrink and their spread drifts over the course of training. Dividing by the running std holds the target at ~O(1) throughout, so gradient magnitudes — and the effective learning rate — stay stable from step 1 to step 100k.

Both centering and scaling are done per rollout depth (a separate RunningNorm for each step of the horizon), because reward spread roughly halves from t0→t3: a single pooled standardiser would take its std from the noisy early depths and hand them ~4× the gradient weight of the late ones. Per-depth standardisation gives every depth a unit-variance target so all depths train evenly. Together, centering + a stationary unit scale are what make one sampled cell per scene (§1.6, K=1) a well-behaved SGD step.

training/train.py:88 · training/stats.py:36–45 
running = [RunningNorm(momentum=cfg.target_momentum, device=device) for _ in range(cfg.train_horizon)]
# RunningNorm.normalize(x): bias-corrected EMA mean/var → (x − mean)/std   (subtract_only → x − mean)

2 · QReg value regression · default recipe

What it is: a regression of the standardised immediate reward onto the network's predicted value at the taken candidate. Despite the name it is not temporal-difference Q-learning — there is no bootstrapping, no target network, no discount, no replay. It is effectively a contextual-bandit / Monte-Carlo action-value regression.

Consumes

RolloutSamples (states collected ε-greedily) + the per-depth standardised target z.

Forward & output

net(feats) → [b·H, A] predicted Q; gather the taken cell → pred_sel [b·H].

Loss

ℒQReg = 𝔼(s,a)~ε-greedy [ ( Q(s,a) − z )² ]
training/train.py:254–256 
pred_sel = pred_all.gather(1, roll.flat_idx[:, None]).squeeze(1)   # Q at the taken candidate
loss = F.mse_loss(pred_sel, target)                              # target = z (per-depth standardised)

Exploration & deploy

  • Rollout actions: ε-greedy — with prob prime_on_policy (default 0.5) the network's own argmax, else a uniform candidate rollout.py:60–68.
  • Deploy: pure argmax over the A candidates (via ArgmaxPolicy). The dueling V(s) term cancels in the argmax, so it changes learning dynamics only, not the policy.
Why regression, not TD? The reward is dense and directly measured at every step, so there is nothing to bootstrap: the "value" being regressed is just the (standardised) immediate payoff of a candidate. Multi-step behaviour comes entirely from the DAgger rollout visiting realistic states — not from credit propagation.

3 · PG policy gradient · REINFORCE family

What it is: the same score map read as policy logits. Trained by the score-function (REINFORCE) estimator with the standardised reward as advantage, on-policy softmax sampling, plus a SAC-style entropy floor and an optional Q-Prop control variate.

Consumes

RolloutSamples whose actions were drawn on-policy (softmax sampling in the rollout) — essential, because the score-function credit must go to the log-prob of samples from the policy being updated.

Forward & output

log π(·|s) = log_softmax(net(feats)); gather the taken cell → pred_sel = log π(a|s).

Base loss

ℒPG = − 𝔼[ z · log π(a|s) ] − α · H(π)
training/train.py:223–237 (elided) 
logp_all = F.log_softmax(pred_all, dim=1)
pred_sel = logp_all.gather(1, roll.flat_idx[:, None]).squeeze(1)      # log π(a|s) at the taken cell
entropy  = -(logp_all.exp() * logp_all).sum(1).mean()               # H(π), for the floor
alpha    = obj.entropy_bonus if log_alpha is None else log_alpha.exp()
loss = -(target * pred_sel).mean() - alpha * entropy                # target = z (advantage)

Dueling is structurally absent under PG: softmax is shift-invariant, so a state-value offset V(s) cancels and cannot be expressed (dueling is a derived property, False for PG).

3.1 · SAC-style entropy floor (automatic temperature)

The entropy coefficient α is not hand-tuned: it is a dual variable driven by ascent on log α to hold mean policy entropy at a target (below ~1 nat is the measured collapse regime). This is the SAC automatic-entropy-adjustment mechanism, applied to a discrete policy — not full SAC (no twin soft-Q critics, no off-policy replay).

log α ← clamp( log α + αlr · ( Htarget − H(π) ) )
training/stats.py:13–20 (entropy_floor_step) · train.py:244–253 
log_alpha += alpha_lr * (target - entropy)          # grow α while H below floor, decay above
log_alpha.clamp_(min=math.log(alpha_min), max=math.log(ALPHA_MAX))

3.2 · Q-Prop control variate optional: qprop=True

A second network (a QReg-style critic) regresses z at the taken cell. The policy gradient becomes score-function on the residual (z − Q) plus the exact analytic gradient of the expected critic value (a sum over all A candidates, cheap because the action set is discrete). Unbiased for any critic quality — a bad critic costs variance reduction, never bias (Gu et al. 2017).

ℒ = − 𝔼[ (z − Q(s,a)) · log π(a|s) ] − Σa' π(a'|s) Q(s,a') − α·H + MSE(Q(s,a), z)
training/train.py:229–235 
crit_sel   = critic(feats).gather(...).squeeze(1)
critic_loss = F.mse_loss(crit_sel, target)
analytic    = (logp_all.exp() * crit_all.detach()).sum(1).mean()   # exact E_π[Q]
loss = -((target - crit_sel.detach()) * pred_sel).mean() - analytic - alpha*entropy + critic_loss

3.3 · Credit assignment: immediate vs return

The reward "signal" fed to the standardiser is either the myopic per-step gain (the recipe) or the Monte-Carlo future-gain sum — the latter makes the objective literally mean CE over timesteps, anchored per scene by t0_ce. This is the one place genuine multi-step credit enters PG.

immediate: signals = rs     return: signals = Σt≥s ( CEt0 − CEt ) / CEt0

else:

4 · Flow continuous-action normalizing flow PARKED — not wired into the trainer

Status. flow/ is a self-contained, experimental module. It is imported only by flow/test_flow.py — training/train.py never touches it. It was the attempt at a continuous action space (a real-valued viewpoint) instead of the 512-candidate grid, distilled from the 2026-07-05 single-scene probes. It is shelved: amortized pathwise training failed at deploy scale, and score-function training is mode-seeking. Treat this section as "how the experiment is built", not a supported training path.

What it is: a ConditionalRealNVP — a normalizing flow over a low-dimensional action R^dim (e.g. the viewpoint's (cy, cx, scale)), each coupling layer conditioned on a context vector (the encoded canvas state), followed by a tanh_box squash into the legal viewpoint box.

Consumes / outputs

How it would be trained

Score-function only. The couplings zero-init to the identity flow, so the initial policy is the base N(0,I) pushed through the squash. Two footguns are designed out: (1) call log_prob on detached samples so the gradient is the pure score function (pathwise through the frozen stack is noise); (2) measure entropy in action space — the flow logdet plus the squash log-jacobian — otherwise the bonus pays the flow to saturate the squash.

ℒflow = − 𝔼[ A · log π(raw.detach() | cond) ] − β · ( logdet + squash_lj )

logp          = flow.log_prob(raw.detach(), cond)        # DETACH: score-function at fixed samples
loss = -(advantage.detach() * logp).mean() - entropy_bonus * (logdet + sq_lj).mean()

Because on-policy reward training is mode-seeking, the docstring notes that a global mode comparison needs a categorical component or value regression upstream — i.e. it does not, on its own, replace the discrete QReg/PG heads.
